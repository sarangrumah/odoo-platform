# custom_retail_import

## Purpose
Productized adapter that converts customer-provided Excel/CSV files into Odoo records, plus an optional direct-from-SFTP recurring feed. Built for the Levi's (PT Sinar Eka Selaras / `levis` tenant) onboarding and reusable for any retail tenant. Generalizes the `custom_bank_import` template/wizard/log trio into per-file-type **import profiles**, and ports the proven `scripts/tenants/era_busana_retailindo` X101 pipeline into the X101 executor.

Answers the three customer questions: (1) Excel→Odoo adapter = the wizard + profiles; (2) read directly from FTP = `retail.import.feed` (paramiko/SFTP + cron); (3) X* master/transaction files = per-`file_type` executors.

## Business Flow
- **Manual import**: Operator opens **Retail Import ▸ Import Data** (`retail.import.wizard`), picks a `retail.import.profile`, uploads a file. `action_preview()` parses the first 20 rows and shows them with NO commit (dry-run). `action_import()` computes `sha256`, blocks duplicates (unless `force`), persists the file to `ir.attachment`, creates a `retail.import.log` (state `queued`), then runs `retail.import.executor.run(log)` — **async via queue_job** (`channel="root.retail_import"`) for large files (`ASYNC_TYPES = {x101,x20,x24,x70d,x32p}`), synchronous otherwise. Falls back to sync if queue_job is unavailable.
- **SFTP feed**: `retail.import.feed` binds an SFTP location + glob to a profile. `ir.cron cron_poll_retail_feeds` (hourly, **off by default**) → `_cron_poll_feeds()` → per active feed, **in `sequence` order**, `_poll_one()` lists files matching `file_glob`, dedups by `retail.import.log` file-hash, stores to `ir.attachment`, and enqueues the same executor.
- **Mailbox feed (19.0.0.9.0)**: `retail.import.mailbox` pulls the nightly X-center reports out of IMAP. `ir.cron cron_fetch_retail_mailboxes` (hourly) → `_cron_fetch_mailboxes()` → per active mailbox `_fetch()` then `_purge()`. `_fetch` writes every attachment to `backup_dir` (`YYYY/MM/`) and copies the `ingest_glob` subset into `drop_dir`, where the ordinary `local` feeds pick it up. The import pipeline is untouched — this is a transport bridge, not a second importer.
- **`cron_poll_retail_feeds` stays DISABLED** through the 19.0.0.9.0 migration. It is the switch that turns a staged file into `pos.order` + journal entries (where `retail_import.x24_post_enabled` is set). Enabling it is an operator decision that must follow the X70D-vs-`pos.payment` Rp 0 reconciliation — never a side effect of a schema upgrade.
- **Executor dispatch**: `run(log)` reads the stored attachment, calls `_load_<file_type>`. Idempotency via `ir.model.data` external IDs under `profile.namespace` (e.g. `levis`).

## Coverage by file_type (executor)
- `x101` — **FULL**. Products: builds 3-level `product.category` (CATEGORY>CLASS>SUBCLASS), `product.attribute` Size+Inseam (`create_variant=always`), `product.template` with `attribute_line_ids` (Odoo auto-generates variants), then matches auto-variants by `(template, frozenset(size,inseam value_ids))` and writes `default_code`=PROD SKU + `barcode`=PROD GTIN. Dedup by SKU keeping latest PRICE EFFECTIVE FROM. Batched commits (200 tmpl).
- `coa` — **FULL**. `account.account` from clean `code,name,account_type`; validates `account_type` against the model selection; Odoo-19 `company_ids` M2M aware (`with_company` + `(4, company.id)`).
- `company` — **FULL**. Writes `res.company` name + partner `vat`/`street`/`phone`/`email`; tolerant of the SES "Label : Value" single-cell layout.
- `x20` — **FULL**. Opening on-hand → `stock.quant` inventory adjustment per store location; resolves variant by barcode(EAN)/default_code(ITEM ID), location by `wh_<storecode>` external ID. ONE-SHOT (guarded: refuses if an `imported` log already exists for the profile).
- `x24` / `x70d` — **DECISION-GATED (Phase 5)**. Parser + transaction grouping ready (`_group_x24`); `run` raises `UserError` until POS representation, history depth, payment-method map and tax mapping are confirmed against a live DB. Target: `pos.order`/`pos.order.line` + `pos.payment`, posted **without moving stock** (X20 already set on-hand).
- `x70d_store` — **STAGED, never posted** (19.0.0.25.0). The X70D a *store* exports, as opposed to the nightly corporate one. Same twelve columns in the same order; columns 11/12 differ. The nightly report heads them `AUTH NUMBER`/`VOUCHER NUMBER` and ships them **empty in every row** (verified: 79 files, 25.414 rows, zero filled); the store export heads them `PAYMENT`/`APPR CODE` and fills them in. `PAYMENT` ("BCA - QRIS", "BRI - DEBIT OTHER") is the only place the acquirer and the card product appear together, and an MDR rate is keyed on exactly that — `TENDER TYPE` cannot substitute: one `OFFLINE_OTHER_CREDITCARD` bucket holds QRIS (0%), on-us debit (0,15%) and off-us credit (1,2%). Staged only: the nightly file is the system of record and already creates the POS orders, so posting this one would duplicate a store's sales.
- `x70t` — **SETTLES THE RESIDUAL, gated** (19.0.0.27.0, `retail_import.x70t_post_enabled`, default OFF). A cross-tab: store × trading day × terminal down the side, one column per tender across the top, and the column set changes nightly because only tenders actually taken get one. Read through `profile.read_wide_records` (header-driven, not index-driven); the report's own `NON CASH(Total)` column is dropped. It posts the **difference** between what X70T reports for a (day, tender, OU) and what that day already settled, so X70D-then-X70T, X70T-then-X70D and the same file twice all book each tender once. Why it exists: see the X70D gap below.
- `x31` / `x32p` / `store_master` — **STAGED**: parsed, counted, attachment kept, no model writes. X32P is reference/audit only (not replayed). Warehouse creation is done by the Track A `scripts/tenants/levis/04_load_stores.py` (Store Master stores are header-wise, not row-wise).

## Key Models
- `retail.import.profile` — Declarative parser config per file type. `read_records(file_b64, limit)` → `{records:[{logical_field: value, _row}], total_rows, blank_rows}`.
- `retail.import.log` — Audit row; `file_hash` (SHA256 dedup), `attachment_id` (kept source), `job_uuid`, `records_created/matched/skipped`, `state` ∈ queued/running/imported/partial/failed. Inherits `mail.thread`.
- `retail.import.executor` — **AbstractModel**; the per-file-type loaders. Delayable via queue_job.
- `retail.import.feed` — SFTP/local source + cron poller. `sequence` fixes poll order.
- `retail.import.mailbox` — IMAP source (stdlib `imaplib`) + retention policy. `retail.import.mail.message` is its per-attachment ledger (uid, uidvalidity, sha256, backup_path, staged_path, state).
- `retail.import.wizard` (TransientModel) — Upload + preview + import.

- `retail.import.mailbox.ingest_glob` (Char) — comma-separated globs; backed-up attachments matching one are also copied to `drop_dir`. Everything else is backup-only.
- `retail.import.mailbox.purge_enabled` / `dry_run` / `retention_days` — three switches, thrown in that order.

## Gotchas / Decisions
- **Two senders, two meanings, one inbox** (19.0.0.26.0). `levis.data@erajaya.com` receives both the X-Store application's nightly output (`xcenteradmin@levi.com` — raw machine data, 169 of 190 messages) and the shops' own manual recaps (`levis.<shop>@erajaya.com` — 19 addresses, the supporting document for the X70D tender, carrying columns the raw feed lacks). A third kind is a person forwarding one of those. `retail.import.mail.message.sender_kind` records which. The test is the **domain**: `@levi.com` is the machine, `@erajaya.com` is a human — and the store prefix `levis.` is matched on the **local part only**, because `levi.com` contains `levi` and a naive substring makes X-Store look like a shop.
- **Filenames cannot carry the ingest decision — headers can** (19.0.0.26.0). On the day the store mailbox was switched on, 19 shops sent 25 attachments in one afternoon; 20 were genuine X70D exports and the glob `X70D*.xlsx` staged **10**. The rest arrived as `Report Sales OLS SES Grand Metropolitan Mall Periode September`, `LAPORAN X70D BULAN SEPTEMBER`, `3. X70D_Tender_Detail_Report OLS PIM 2`, `18-REPORT-SALES ...`. So `retail.import.mailbox.ingest_signature` (`TRANSNUM,TENDER AMOUNT`) opens the workbook and decides on what a sheet's header contains. With it set, `ingest_glob` is `*.xlsx` and naming is irrelevant: the three "LAPORAN HARIAN" retypes and two manual recaps carry no such sheet and are backed up only. Verified against all 25 real attachments: 20 staged, 5 refused, no false positives.
- **The nightly mailbox deliberately still decides by filename.** Its files are machine-named and run to 7 MB; opening each one to prove what it is would be waste. `ingest_signature` is empty there, and `_should_ingest` falls back to the glob.
- **A signature may only name columns that never move** (19.0.0.26.0). The *same* workbook heads column 11 `Payment Method` on its 1 September tab and `PAYMENT` on its 17 September tab (Kelapa Gading, sha256 `cd37ba4c…`). Anchor on `TRANSNUM` and `TENDER AMOUNT`; never on the acquirer caption. For the same reason the profile maps by **column position**, not by caption.
- **Per-sheet, not per-workbook** (19.0.0.26.0). `profile.header_signature` skips tabs that do not match, so a workbook mixing X70D tabs with something else parses only the X70D ones — PIM 1 sent 18 tabs of which 17 are X70D, Manado Town Square 7. Previously `all_sheets` parsed every tab and `require_fields` had to catch the debris downstream.
- **The subject names the store, and it is checked against the file** (19.0.0.26.0). Shops write the code in the subject — `LAPORAN SALES 80432 18092026`, `(0020080747)`, `20080741` — and it matches `stock.warehouse.l10n_store_code` exactly. `ingest_store_check` refuses to stage a workbook whose STORE CODE column disagrees: two independent statements of the same fact, and a disagreement means a shop attached another outlet's export. Parsing the subject abstains on ambiguity and must reject the date sitting right beside the code (`18092026`).
- **STORE CODE cells are numeric** (19.0.0.26.0). openpyxl returns `80744.0`; the last five characters of that are `744.0`, which matches no store and would make a file disagree with its own subject. `_store_code_text` drops the fraction before reading digits.
- **Three shops export X70D without the acquirer column at all** — PLAZA SENAYAN, METROPOLITAN MALL BEKASI, BALIKPAPAN SUPERBLOCK. Their files are staged (they are valid X70D) but carry nothing to price MDR with. That is a fault at source, not something the parser can repair.
- **The data files are `noupdate="1"`**, so a tenant whose mailbox and profile already exist never receives new fields from the XML. `migrations/19.0.0.26.0/` re-points them, and only where the old filename glob is still in place. Attachments already fetched under the old rule are **not** rewritten — their ledger rows are complete and their backups verified; the backlog is a one-off file copy from `backup_dir` to `drop_dir`.
- **The store X70D must not share the nightly drop dir** (19.0.0.25.0). Stores name their export `X70D_Tender_Detail_Report -OLS MKG SEPTEMBER 2026.xlsx`, which matches `feed_levis_x70d`'s own `X70D*.xlsx` glob. Dropped beside the nightly file it is imported as a nightly file and **duplicates that store's sales**. Hence a separate feed on `/mnt/data_levis/data_store` and a separate mailbox backing up to `/mnt/data_levis/mailbox_store`.
- **Two mailboxes, one INBOX, disjoint senders** (19.0.0.25.0). `mailbox_levis_xcenter` filters `XcenterAdmin@levi.com`; `mailbox_levis_store_tender` filters `erajaya.com`. IMAP SEARCH cannot express "not from X", so the separation rests entirely on those addresses — **do not blank either filter**, or the two records fetch the same mail and the purge in one deletes what the other has not read. Purge stays OFF on the store mailbox: stores send weekly and cumulative, so an old message is still the only copy of the weeks it covers.
- **Weekly cumulative files are staged append-only, not de-duplicated** (19.0.0.25.0). A store resends the whole month each Saturday, so the same trading day arrives repeatedly, and `_persist_lines` always creates. That is deliberate: staging stays a record of what was received, and it is what lets a store correct a week by resending it. Any reader of `x70d_store` rows must therefore resolve a transaction to its **most recently imported** row (`DISTINCT ON (store_code, trans_date, register, transnum) … ORDER BY … id DESC`) — summing the staged rows would multiply.
- **`all_sheets` / `require_fields` on the profile** (19.0.0.25.0). The store export puts one trading day per worksheet, each with its own header, and ends every sheet with a TOTAL row that carries an amount and no store code. `all_sheets` reads every tab applying `data_start_row` per tab; `require_fields` drops rows that cannot identify themselves and counts them as blank, so `total_rows = kept + blank_rows` still holds.
- **`APPR CODE` is an identifier, not a number** (19.0.0.25.0). Real files carry `007403` beside `Tgccbw` and `R68223`. Excel types the column numerically and openpyxl then returns `7403`, losing the leading zeros that the acquirer's settlement reference actually has. `payment`, `appr_code`, `cashier_id` and `cashier_name` are therefore in `TEXT_FIELDS`.
- **`_stage_only` commits through `_ri_commit`** (19.0.0.25.0), not `cr.commit`. A raw commit escapes a `TransactionCase` rollback, which is why every stage-only loader used to be untestable.
- **openpyxl must be in the Odoo image** for in-container `.xlsx` reading — added to `odoo/requirements.txt` (xlsxwriter in the image is write-only). `paramiko` added for SFTP. **Rebuild the image** before installing this module.
- **Large files run async** to dodge the reverse-proxy `ERR_EMPTY_RESPONSE` timeout on long synchronous web requests. The X101 import is ~30 min for ~160k variants. queue_job runner must be active (odoo-mgmt loads `queue_job` via `SERVER_WIDE_MODULES`).
- **Idempotency**: master data (products, categories, accounts) via `ir.model.data` external IDs (`noupdate=True`); transactions via file-hash + per-row external IDs; X20 opening stock is a guarded ONE-SHOT (re-applying would double on-hand).
- **SFTP credentials are stored raw** in `ir.config_parameter` — the platform has no at-rest decryptor yet (the adapter-framework `enc:` convention is aspirational). Restrict parameter read access; prefer key-based auth.
- **Data reality (Levi's, 2026-06-11)**: the delivered X20/X24/X70D are **single-store samples** (store 14694 only). X101 + CoA are full. The 24-store list comes from the Store Master (names only — no store codes for 23 of 24). The store-code→warehouse crosswalk and full multi-store transactions are blocked on the customer providing complete store-coded extracts (or the live SFTP feed). See `scripts/tenants/levis/README.md`.
- **POS history is the chosen model** for X24 (not sale.order) — register/cashier/tender/member map ~1:1 to POS. Gated on Phase-5 decisions.
- **X101 data-quality (v19.0.0.2.0)**: (1) `_clean_str` scrubs spreadsheet error sentinels (`#N/A`, `#REF!`, `#VALUE!`, …) to `""` so they no longer leak into category names/SKUs/barcodes (a real category literally named `#N/A` was observed — openpyxl `data_only=True` returns cached VLOOKUP errors as strings). (2) X101 merchandise is created **storable** (`is_storable=True`, type `consu`); the **"Original cut" tailoring service** → `type="service"`, detected by `ir.config_parameter` `retail_import.service_product_codes` (exact code) or `retail_import.service_category_keywords` (substring). **Both default EMPTY** — a substring default like `TAILOR` false-matched 102 real merchandise rows in rnd_levis ("TAILORED BUSTIER", "TAILORED CLASSIC" shirts), so everything is storable merchandise until the actual service marker is configured. (3) Rows with a **blank category** or **zero/unparseable price** are flagged `state=error` on `retail.import.line` (bumps `error_count` → log state `partial`) but still imported (no silent data loss). Remediate already-imported DBs with `scripts/tenants/levis/71_fix_retail_import_dataquality.py` (dry-run default; `RETAIL_FIX_APPLY=1` to write).
- **X101 multi-GTIN + variant backfill (v19.0.0.3.0)**: depends on `custom_product_barcode`. (Fix A) every GTIN of a SKU is registered as a `product.barcode` alternate on the variant (`_x101_register_gtins`) — a Levi's SKU has several GTINs and the variant's single `barcode` field holds only one; X20/X24/X48 barcode lookups switched to `product.product._resolve_barcode` so any scanned code resolves. (Fix B) re-running X101 now backfills newly-appearing Size/Inseam values onto an already-registered template (`_x101_backfill_template_attrs`) so missing variants regenerate, instead of skipping the template outright.
- **Mailbox retention keys off the BACKUP, never the IMPORT (19.0.0.9.0)**. `_purge` re-reads each backup off disk and re-checks its SHA256 before it flags `\Deleted`; a failed import still has raw bytes in `backup_dir` + `drop_dir` and gets retried by the feed. Coupling deletion to import success would let a parser bug destroy source data that exists nowhere else. Deletion is `UID STORE +FLAGS (\Deleted)` then `UID EXPUNGE <uid>` (the server advertises `UIDPLUS`); nothing is copied to Trash, which would double the storage the purge is trying to reclaim.
- **The X-center mails carry a CONSTANT filename** every day (`X24DN_Retail_Sales_Detail_Report.xlsx`). `_suffixed_name` appends `__<sentUTC>` (a *suffix*, so `X24*.xlsx` still matches) — otherwise day N+1 silently overwrites a day-N file that failed to import and is still sitting in `drop_dir`. The stamp is provenance only; business dates come from inside the file.
- **`mail.erajaya.com` reports no quota** (`GETQUOTAROOT` returns empty) even though it advertises `QUOTA`, so retention must be self-managed: `retention_days` plus a `max_messages`/`max_bytes_mb` emergency drain that logs a warning rather than truncating silently. Volume is ~10.4 MB/day across six attachments.
- **`imaplib` returns the bare UIDVALIDITY value** (`response("UIDVALIDITY") -> ('UIDVALIDITY', [b'1'])`), not the `[UIDVALIDITY 1]` bracket. `_uidvalidity` accepts both; parsing only the bracket silently yields `""`, which disables the UID bookkeeping purge depends on.
- **`retail.import.mailbox` must be `active` in exactly ONE database.** The cron runs per-DB; two DBs polling the same INBOX would race to delete each other's messages. `_lock()`'s `pg_try_advisory_lock` only guards workers *within* one database. It is session-scoped on purpose: `_fetch` commits per message, which would release a `FOR UPDATE` row lock.
- **Do not name a One2many `message_ids` on a `mail.thread` model** — it shadows the chatter's own field. The mailbox ledger is `fetched_ids`.
- **X20 must stay out of the mailbox ingest set.** `_load_x20` is a guarded one-shot opening-balance loader, and the emailed X20 is `.xlsx` with a 14-column layout that the existing CSV profile (columns 16–29) cannot read. Same for X32P/X70T (staged-only). Only X24/X70D/X31 are in `ingest_glob`.
- **Storable ⇒ POS must still not move stock**: making merchandise storable means POS session-close would otherwise create pickings (Odoo gates this on `pos.session.update_stock_at_closing`, derived from company config). The X24/X48 executors force `update_stock_at_closing=False` on import-created sessions (post-create, since `pos.session.create` overrides it) so the financial-only replay never double-counts the X20 on-hand snapshot. The `:1002` guard (`UNEXPECTED n stock move(s) on close`) is the tripwire.
- **The source workbook is the source of truth for tax, and `price_subtotal` cannot deliver it.** POS session close ignores the stored `price_subtotal`: it rebuilds base lines from `price_unit`/`qty`/`tax_ids` and re-runs the tax engine (`pos.session._accumulate_amounts`). X24DN truncates net per line (`net = trunc(total/1.11)`, `tax = total - net`) while Odoo rounds tax *globally per order*, so deriving the tax drifts by 1 rupiah on 7,151 of 12,841 lines (Rp 7,145.52/month; X48 Rp 5.40). The importer therefore stores the file's own figures on `pos.order.line.ri_src_net`/`ri_src_tax` and `custom_retail_import_pos` feeds them to `account.tax`'s **`manual_tax_amounts` / `manual_total_excluded`** base-line keys. Those keys are annotated *"TO BE REMOVED IN MASTER"* in `account/models/account_tax.py` — they work in 19.0; if a future version drops them, fall back to a post-close true-up entry against VAT Output.
- **`manual_total_excluded` must carry the sign of `quantity * price_unit`, never `abs()`.** X24DN records an in-transaction exchange as a `qty=-1` line paired with a `qty=+1` line of the same item *inside a sale order*. `abs()` turns the reversal into a second sale (revenue and VAT booked twice, the unmatched tender plugged to Cash Difference Loss). The order-level `sign` is applied downstream and is not enough.
- **`custom_retail_import` must NOT depend on `point_of_sale`.** `trn_arkaaim` runs the importer without POS, and a hard dependency would force-install the POS application there. The `pos.order.line` fields + override live in the `auto_install` bridge `custom_retail_import_pos`; the executor guards its writes with `"pos.order.line" not in self.env`.
- **X24DN's NET DISCOUNT AMOUNT is the single discount source, booked verbatim.** Joining X24DN and X31 on `(store, date, transnum, product_code, waist, inseam)`: X31 covers *every* discounted X24 line (0 X24-only), 647 keys differ by ±1 rupiah, and 15 X31 rows have no X24 counterpart (Rp 5,344,249). So `retail_import.x24_discount_reclass` and `retail_import.x31_post_enabled` are mutually exclusive — enabling both grosses `Gross Sales` up twice. `_ri_validate_discounts` reports the three buckets before posting. The reclass books **Dr Sales Discount-`<cat>` / Cr Gross Sales-`<cat>` at the file's figure, never divided by 1.11**: both legs carry the same number, so it balances exactly and adds no selisih.
- **The discount reclass must reuse the product resolved by `_post_x24`.** X101 variants are keyed on `code+waist+inseam`, so a `default_code == item_code` lookup misses most rows (it found only Rp 164m of Rp 1.41bn).
- **EBR reports append a `Grand Total` footer row** whose `ITEM CODE` is `''`, not `None` — an `is None` guard lets it through and it becomes a bogus parked transaction that doubles the file's totals. `_ri_drop_footer_rows` strips it from X24/X31/X48.
- **Archived stores still transact.** `resolve_config` reaches a `pos.config` by xid regardless of `active`, so an archived store accepts orders — but its session cannot close (`account.move._post` refuses the archived Operating-Unit analytic on `pos.config.warehouse_id.l10n_ou_analytic_id`), leaving it in `closing_control` with **no GL at all** while the import still reports success. `_ri_assert_stores_postable` fails fast; `_ri_pos_configs` also seeds tender/SUSPENSE methods onto archived configs (a plain `search([])` skipped them, so their orders died with *"The payment method selected is not allowed in the config of the POS session"*).
- **X24 auto-maps unmapped stores before import.** `_x24_automap_missing` runs at the start of the X24 pass: for each store in the batch with no `posconfig_<code>` xid yet it delegates to `_x24_map_stores_to_configs` (commit=True), which writes a mapping only on a UNIQUE exact/containment name match. Ambiguous or unmatched stores are left alone and their rows keep failing with the same actionable "no pos.config" message — so a newly opened/reactivated store no longer needs a manual mapping run first, but a genuinely ambiguous one still does.
- **One POS session per (store, trading day), oldest day first.** Odoo forbids a second non-closed session on the same `pos.config`, so the importer used to open ONE session per store for the whole file — collapsing Gross Sales, VAT, POS Suspense, the tender settlement and the discount reclass of every day onto the file's *last* trans date. `_x24_day_batches` batches the orders per `trans_date` and `_pos_close_and_backdate` closes each day's sessions before the next day opens its own, so each day's entries carry that day's date. This needs `retail_import.x24_close_sessions=1` (with closing off there is no GL to date, and the import keeps the legacy single-session shape). Cost: a 20-day × 21-store file goes from 20 session closes to ~240.
- **Backdating a move means three tables, not one.** `account.move.line._create_analytic_lines` copies the line's date at **post** time, so an entry posted today and re-stamped afterwards leaves its Analytic Items dated today — the per-OU P&L then reports the whole import in the wrong period while the journal entry itself looks right. `_ri_restamp_move_date` updates `account_move`, `account_move_line` **and** `account_analytic_line`. `_pos_close_and_backdate` also re-stamps `pos_session.start_at/stop_at`, which are otherwise "now".
- **The POS close emits more than its own entry when `x24_decouple_payment` is OFF.** With real tenders joined from X70D, `_create_account_move` also produces one `account.payment` per bank tender and one `account.bank.statement.line` per cash tender, all dated at close (the import day) while the sale sits on its trading day — 1,036 payments + 364 cash lines stranded in July on rnd_levis. Both models carry `pos_session_id`, so `_ri_backdate_session_payments` reaches them and runs each through `_ri_backdate_move` (dates + sequence-month realignment). Decouple mode never hits this: its SUSPENSE method is `pay_later`, so the close writes neither.
- **The X24DN discount reclass lives INSIDE the store's POS closing entry, not in its own journal.** `custom_retail_import_pos.pos_session._create_account_move` appends `Dr Sales Discount-<cat>` / `Cr Gross Sales-<cat>` to `move_id` while it is still draft (core posts it right after, and `check_move_validity=False` is already in context; the added legs are balanced pairs so `_check_balanced` still passes). A session is one store on one trading day, so the discount is automatically per store, per date, next to the Gross Sales / VAT / Suspense it belongs to, carrying the same OU. `_post_x24_discount_reclass` now only cross-validates against X31 and reports unmapped discount — it posts nothing. **No RIADJ move is produced for X24 any more**; RIADJ remains only for X31.
- **The daily split applies to every entry the import produces, not just the POS close.** `_post_x70d_reconcile` posts one RIREC transfer per tender date and `_post_x48` batches refunds per day too. A single move dated at `max(date)` is the bug, not the design.
- **Every closing-entry line carries the store's Operating Unit, not just the sale lines.** `custom_levis_localization.pos_session` stamps `_get_sale_vals` **and** `_get_tax_vals` / `_get_combine_receivable_vals` / `_get_split_receivable_vals`, so VAT Out and the POS Suspense / per-tender receivable are sliceable per store. `analytic_distribution` is set explicitly in the vals (a stored compute with `readonly=False` keeps a create-time value) because the `l10n_ou_analytic_id` trigger in `account.move.line._compute_analytic_distribution` skips `display_type` `'tax'` and `'payment_term'`. The hand-built reclass / settlement moves use `_ri_ou_line_vals`, which degrades to `{ou_id: 100}` when the levis localization is absent. The X70D transfer credits the suspense **per OU** so each entry balances within its own Operating Unit.
- **A negative `NET SOLD QUANTITY` on an X24DN line is a return, not a negative sale.** X24DN books an in-store exchange as a `qty=-1` line paired with a `qty=+1` one inside the *same sale* transaction. Left alone it debits `Gross Sales-<cat>`; it must go to `Sales Return-<cat>` (53xxxxx). `_post_x24` therefore sets `ri_is_return` on those lines and the bridge's `_prepare_base_line_for_taxes_computation` repoints the account — the same path X48 refunds use. Jun-2026: 14 file rows, Rp 15.719.455, all textile.
- **A `TS…` code does not mean "tailoring service".** The `x24_np_service_prefixes` heuristic files every `TS`-prefixed non-merchandise line under `Labor (Service)`, but Levi's issues `TS…` codes to sold *goods* too — Fodable Cup, Levi's Pin, TAB, Patches M/L, BUTTON/PCS (Rp 8.243.227 of Jun-2026 revenue). List those exact codes in `retail_import.x24_np_goods_codes` (comma-separated) and `_x24_np_category` routes them to `x24_np_category_id` (Miscellaneous) instead. A lazy-created product is only categorised at creation, so an already-imported DB needs `20_reset_txn.py` (it drops the lazy products) plus a re-import before the GL follows.
- **`Sales untaxed` lines worth 0,00 in the POS closing entry are expected, not a bug.** 170 Jun-2026 rows have `TOTAL AMOUNT = 0` and a blank `TAX RATE` — 169 are 100 %-discounted giveaways (`gross = NET DISCOUNT`, `NET SOLD = 0`) and one is a zero-priced tailoring service. They get no `tax_ids`, so `pos.session._get_sale_key` groups them separately and `_get_sale_vals` names the group *"Sales untaxed"*; the amount is genuinely zero. The line records that the goods left the store; its revenue is grossed up by the discount reclass instead.
- **X24DN has four discount slots, and at least two are in real use** (1,701 of 11,497 June rows populate `DISCOUNT AMOUNT 2`). `NET DISCOUNT AMOUNT` stays the GL figure; the slots explain it. `_x24_discount_slots` folds them into `ri_discount_type` / `ri_discount_code` / `ri_discount_description` on the line, and the reclass groups by `(income, discount acct, OU, code, description)` so each RIADJ line names its promo (e.g. `LPAID1117 CRM-VIP DISCOUNT`). A slot total that disagrees with `NET DISCOUNT AMOUNT` is counted and reported on the log — never silently reconciled.
- **X70D silently drops every acquirer-level tender; only X70T reports them (19.0.0.27.0).** Levi's POS began issuing acquirer-coded tenders on **16-Sep-2026** — `BCA_QRIS`, `BCA_DEBIT_GPN`, `BCA_DEBIT_OTHER`, `BCA_CARD`, `BCA_REGULAR_ON_US`/`OFF_US`, `BCA_UNION_PAY_OFF_US`, `BRI_DEBIT_GPN`, `BRI_DEBIT_OTHER`, `BRI_QRIS`, `BRI_REGULAR_OFF_US`, `MANDIRI_DEBIT_OTHER`, `MANDIRI_QRIS`, `OFFLINE_BANK_TRANSFER` — and the nightly X70D does not carry those rows **at all**: not late, not under a coarse code, not in any later file. Measured over 87 nightly X70T/X70D pairs (29-Jun … 24-Sep-2026): the two agree **to the rupiah** on every day that used only the old `OFFLINE_*`/`CASH` vocabulary, and X70D is short by **exactly** the acquirer-coded total on every day that did not (Rp 389.478.201 over 16–24 Sep; Rp 188.976.100 on 24-Sep alone = 32 % of the day). X24DN is unaffected — its per-store sales equal X70T's per-store tender to the rupiah for all 31 stores — so the whole difference stays on POS Suspense Clearing. Do **not** try to infer the acquirer from `TENDER TYPE`: one `OFFLINE_OTHER_CREDITCARD` still mixes QRIS, on-us debit and off-us credit. The 14 codes map 1:1 onto the `levis.mdr.rate` labels seeded in `custom_levis_mdr` (`BCA_QRIS` → *BCA - QRIS*, `OFFLINE_BANK_TRANSFER` → *TRANSFER*), which is what makes MDR computable from the corporate feed without the weekly store exports.
- **The settlement guard fires on the first clean import, not on a duplicate.** `_post_x70d_reconcile` (like `_post_x24` / `_post_x31` / `_load_x20`) refuses to run while **any** other log of the same profile sits in state `imported`. Nightly X70D logs normally land on `partial`, so the guard is invisible — until one file imports with `error_count == 0`, after which every later file of that profile raises *"X70D already reconciled (log #N)"*. Catching up four nights by hand in Sep-2026 meant flipping each finished log back to `partial` between files. The X70T loader deliberately does **not** copy this guard: netting against `_ri_settled_by_tender` makes re-running it a no-op, which is a stronger guarantee than a state flag.
- **`data/retail_import_profiles.xml` is `noupdate="1"`.** Widening a column map only reaches fresh installs; existing tenants need a `migrations/<version>/post-migration.py` that merges the new keys into `column_map_json` (see 19.0.0.10.0 for X48, 19.0.0.12.0 for X24DN).
- **Known, pre-existing:** X48 refunds are tendered against the store's CASH method, and the refund total lands in `Cash Difference` on the cash journals rather than reducing Cash on hand. Unrelated to the tax/COA work above; not yet fixed.
- **A numerically-typed cell is the identifier bug, not the dot (19.0.0.23.0).** Excel types a whole column numerically as soon as one cell looks like a number, so the first Levi's half size (`10.5`) turned ITEM SIZE numeric and openpyxl returned floats — `(r.get("size") or "").strip()` then killed the whole X101 upload with `AttributeError: 'float' object has no attribute 'strip'`. The silent half is worse: a numeric GTIN column would write `4550703351542.0` into `barcode`, and a size of `10.0` creates a second `product.attribute.value` beside the `10` already there. `retail_import_profile._number_to_text` is now the single de-floating rule (`10.0`→`"10"`, `10.5`→`"10.5"`, never scientific notation), applied by the reader to an **allowlist** of identifier columns (`TEXT_FIELDS`) — a denylist would have swallowed the amount/date columns that `_parse_amount`/`_parse_date` need as native types, and an unlisted field keeps the old behaviour. The X101 seam re-applies it defensively because the MDM API enters without the reader, and `_x24_codepart` is a thin wrapper over it so the XLSX and MDM paths cannot drift. Rows replayed out of `raw_data_json` were staged *before* the coercion, so `_ri_normalize_row` runs on read or a fresh import's `"1"` key stops matching an older log's `"1.0"`.
- **Half sizes also broke the supplier-code translation.** `_X101_HYPHEN_RE`/`_X101_SKU_RE` rejected a fractional tail, so 908 codes like `008M8-000010.5` never resolved to their PROD SKU. The tail now admits exactly one fraction (`(?:\.[0-9]+)?`), so `ABCDE-1234..` still fails. Separately, `_search_x101_product_code` only handled the scalar operators — **Odoo 19 rewrites `=` into `in` before a `search=` method is reached**, so the translation branch never ran and the field matched nothing, for any code, with no error. The `in` branch must treat the value as "iterable and not a string": Domain hands it an `OrderedSet`, and wrapping that in a list raises `TypeError: unhashable type: 'OrderedSet'` deep inside `optimize_full`.
- **One POS session opened from the UI used to kill the whole night's import (19.0.0.24.0).** `get_session` called `pos.session.create()` blind, and Odoo permits at most one non-closed session per register — so a cashier who clicked *Open Register* made the create raise `ValidationError: Another session is already opened for this point of sale`, which propagated out of `_load_x24` and aborted the **entire file**, not just that store. In `prd_levis_begbal` an empty session left in `opening_control` on 10-Aug-2026 cost eight consecutive nights of sales. `_ri_open_session` (shared by X24 and X48) now **adopts** an existing session that holds no orders, and raises `RetailSessionBusy` for one that does — the caller parks that store's rows via `fail_rows` and imports every other store. A live shift is never hijacked: its takings would land in the import's closing entry.
- **A dead import stays `running` forever, and `running` also blocks re-import.** `executor.run` commits `state='running'` *before* the handler starts (deliberately — it is how "still going" is told apart from "died an hour ago"), so a handler that raises leaves the row running, and `find_duplicate` counts `running` as success, so the same file can never be retried. The pair is invisible: the next hourly poll archives the file as a duplicate and the feed still reports `last_status=ok`. `retail.import.log._cron_flag_stuck` (hourly, threshold `retail_import.stuck_hours`, default 6) flips such rows to `failed`, which both surfaces them and lets the next poll retry the file. The outside-in check is `scripts/ops/retail_import_check.sh` — it alerts on stuck/failed logs, erroring or silent daily feeds, and on `pos_order` going stale, which is the only one of those that measures the outcome rather than the machinery's opinion of itself.
- **This module's groups sit on its own `custom_retail_import.res_groups_privilege_retail_import` privilege** ("Retail Import") — Odoo 19 renders every group sharing one `res.groups.privilege` as a single pick-one dropdown on the user form, so a privilege shared across modules makes saving a user silently drop the other modules' groups. The privilege carries `custom_core.module_category_custom_platform`, so the selector still appears alongside the other custom modules. Do not point new groups at `custom_core.res_groups_privilege_custom_platform`.
