1. Sebelum Mulai

Getting started

1.1 Cara Membaca Panduan Ini

Panduan disusun per peran pengguna. Cari bab yang sesuai dengan pekerjaan Anda — Anda tidak perlu membaca bab lain.

Simbol yang dipakai:

SimbolArti
Invoicing ▸ Vendors ▸ BillsJalur menu. Klik berurutan dari kiri ke kanan.
[Confirm]Tombol yang harus diklik.
Purchase TypeNama field pada form.
PO/T/EBR/…Nilai atau kode teknis.
PERANPeran yang berwenang melakukan langkah tersebut.
Kotak peringatan

Kotak berwarna kuning berisi hal yang sering salah. Kotak merah berisi hal yang akan menyebabkan kegagalan bila diabaikan. Bacalah sebelum menjalankan langkahnya.

1.2 Login & Mengenal Layar Odoo

  1. Buka alamat Odoo di browser. Isi Email dan Password, lalu klik [Log in].
  2. Anda akan tiba di layar Home yang menampilkan semua aplikasi yang boleh Anda akses. Aplikasi yang tidak muncul berarti peran Anda tidak memiliki aksesnya.
  3. Klik ikon kotak-kotak di pojok kiri atas kapan saja untuk kembali ke Home.
  4. Nama perusahaan (PT. ERA Busana Retailindo) tampil di pojok kanan atas.

2. Ops / Data Admin — Retail Import

Retail Import / Manager Menarik data penjualan & master dari EBR ke Odoo
Apa yang Anda kerjakan

Penjualan Levi's tidak diketik di Odoo. Penjualan terjadi di sistem kasir EBR, lalu di-export sebagai berkas Excel/CSV ("berkas X"), dan Anda yang memasukkannya ke Odoo. Odoo kemudian membentuk POS Order dan jurnalnya secara otomatis.

2.1 Impor Berkas Secara Manual

Retail Import ▸ Import Data

  1. Buka menu di atas. Sebuah jendela Import Data akan muncul.
  2. Pilih Profile sesuai jenis berkas — misalnya levis_x24 untuk penjualan harian, levis_x70d untuk data alat bayar, levis_x101 untuk master produk.
  3. Klik [Upload your file] pada Source File dan pilih berkas dari komputer Anda. Field File Type akan terisi sendiri mengikuti Profile.
  4. Klik [Preview (dry-run)] lebih dulu — jangan langsung Import. Preview menampilkan 20 baris pertama hasil pemetaan kolom, tanpa menulis apa pun ke database.
  5. Periksa hasil Preview: apakah kolom terbaca di tempat yang benar? Jika kolom bergeser atau kosong, berarti format berkas dari EBR berubah — hentikan dan perbaiki Import Profile (§2.4).
  6. Jika Preview benar, klik [Import]. Berkas besar diproses di latar belakang (X101 bisa ± 30 menit); Anda boleh menutup jendela.
Centang Force re-import hanya bila Anda benar-benar bermaksud mengulang

Secara normal, berkas yang sudah pernah diimpor akan dilewati (lihat kotak di bawah). Mencentang Force re-import mematikan pengaman itu dan memaksa berkas diproses ulang. Gunakan hanya setelah impor sebelumnya gagal dan Anda sudah yakin penyebabnya diperbaiki.

Tidak perlu takut impor ganda

Setiap berkas di-hash (SHA256). Jika Anda tidak sengaja mengunggah berkas yang sama persis dua kali, sistem akan melewatinya — tidak akan terjadi pembukuan ganda.

Urutan impor itu penting

Impor X101 (master produk) lebih dulu, baru X24DN. Jika ada SKU di X24DN yang belum ada di master, transaksi tersebut akan diparkir sebagai error — bukan diposting dengan produk asal-asalan. Ini disengaja, agar pendapatan tidak bocor ke akun yang salah.

Urutan harian yang benar: X24DN → X70D → X48.

2.2 Memantau Hasil Impor

Retail Import ▸ Imports

Daftar ini adalah catatan seluruh impor yang pernah dijalankan. Kolom yang perlu Anda perhatikan: State, Records Created, Records Matched, Records Skipped, dan Error Count.

StateArtiTindakan Anda

2.3 Menangani Impor Berstatus Partial / Failed

  1. Klik baris impor yang bermasalah untuk membuka detailnya.
  2. Lihat Error Count dan buka tab baris. Baris yang gagal ber-state error, dengan pesan penyebabnya.
  3. Penyebab paling umum:
    • SKU tidak ada di master → impor ulang X101 (versi terbaru), lalu impor ulang berkas ini.
    • Kolom bergeser / kosong → format berkas EBR berubah. Perbaiki Column Map di Import Profile (§2.4).
    • Nilai #N/A atau kategori kosong → data sumber cacat; minta EBR mengirim ulang.
  4. Setelah penyebabnya diperbaiki, impor ulang berkas yang sama. Baris yang sudah sukses tidak akan diposting dua kali.

2.4 Import Profiles — Pemetaan Kolom

Retail Import ▸ Configuration ▸ Import Profiles

Hanya untuk Retail Import / Manager

Mengubah Import Profile mengubah cara seluruh berkas dibaca. Salah sedikit, seluruh impor berikutnya akan salah. Ubah hanya bila format berkas dari EBR memang berubah, dan selalu uji dengan [Preview] sebelum dipakai produksi.

Field yang penting pada Profile:

FieldFungsi

File TypeMenentukan logika pemuatan mana yang dipakai (X101 ≠ X24 ≠ X70D).

Data Start RowBaris ke berapa data dimulai (dihitung mulai dari 1). Ini paling sering menjadi penyebab impor kacau — jika EBR menambah baris judul, angka ini harus disesuaikan.

Fix EncodingMemperbaiki karakter rusak (mis. ® yang terbaca salah).

2.5 Import Feeds (SFTP) & Mailboxes

Retail Import ▸ Configuration ▸ Import Feeds · … ▸ Mailboxes

Selain upload manual, berkas dapat masuk otomatis. Import Feed memindai folder SFTP/lokal; Mailbox menarik lampiran dari INBOX email. Keduanya dijalankan oleh Scheduled Action.

Dua aturan yang tidak boleh dilanggar

1. Record Mailbox hanya boleh aktif di SATU database. Dua database yang memantau INBOX yang sama akan saling menghapus email.

2. Impor otomatis baru berjalan setelah Scheduled Action "Retail Import: poll feeds" diaktifkan (lihat §10.2). Selama nonaktif, berkas hanya menumpuk di folder tanpa diproses.

3. Store Supervisor — Point of Sale

Point of Sale / Manager Memantau penjualan toko hasil impor
Penting dipahami

Di Odoo, POS Order dan Session toko Levi's dibentuk oleh proses impor, bukan diketik kasir. Tugas Anda adalah memverifikasi bahwa angka di Odoo sama dengan angka di sistem EBR.

3.1 Dashboard & Sesi POS

Point of Sale ▸ Dashboard · Point of Sale ▸ Orders ▸ Sessions

Sistem membuat satu sesi per (toko × hari dagang). Sesi ditutup otomatis dan jurnalnya diberi tanggal hari dagang — bukan tanggal impor. Jadi laporan bulan Juni tetap berisi transaksi Juni, meskipun berkasnya baru diimpor bulan Juli.

3.2 Memeriksa Order Hasil Impor

Point of Sale ▸ Orders ▸ Orders

  1. Gunakan Filters dan Group By untuk menyaring per toko atau per tanggal.
  2. Klik satu order untuk melihat barisnya: produk, kuantitas, harga, pajak, dan diskon.
  3. Bandingkan totalnya dengan laporan X24DN dari EBR. Seharusnya sama persis (selisih Rp 0).

3.3 Memeriksa Jurnal Penutup Sesi

  1. Buka sesi dari Point of Sale ▸ Orders ▸ Sessions.
  2. Klik tombol pintas [Journal Entries] untuk melihat jurnal penutup sesi tersebut.
  3. Periksa bahwa setiap baris membawa Operating Unit toko yang benar.
Indikator kontrol utama

Setelah X24DN dan X70D untuk suatu hari terimpor, saldo akun POS Suspense Clearing untuk hari itu harus NOL. Saldo yang tersisa berarti data alat bayar (X70D) belum masuk. Laporkan ke Ops/Data Admin.

4. Purchasing Officer & Manager

Purchase / User · Purchase / Manager Pengadaan barang dan jasa

4.1 Membuat Purchase Order (Trade / Non-Trade)

Purchase ▸ Orders ▸ Purchase Orders → klik [New]

  1. Isi Vendor.
  2. Pilih Purchase Type — ini keputusan terpenting di form ini:
    • Trade — barang dagangan (produk Levi's yang akan dijual di toko).
    • Non-Trade — segala hal lain: ATK, jasa, sewa, perbaikan, konsultan.
  3. Isi Deliver To — pilih warehouse tujuan. Warehouse inilah yang menentukan Operating Unit yang akan menempel pada seluruh jurnal PO ini.
  4. Tambahkan produk pada tab Products: kuantitas, harga satuan, pajak.
  5. Klik [Confirm Order].
Purchase Type tidak bisa diubah sembarangan setelah Confirm

Pilihan Trade / Non-Trade menentukan tiga hal sekaligus: nomor dokumen, akun hutang, dan akun GR/IR.

Purchase TypeNomor POAkun Hutang
TradePO/T/EBR/2026/07/xxxHutang Dagang 2103100001
Non-TradePO/NT/EBR/2026/07/xxxHutang Non-Dagang 2103300001

Salah pilih = hutang masuk ke akun yang salah dan nomor dokumen tidak sesuai kebijakan EBR.

4.2 Persetujuan PO

Approvals Purchasing Manager

  1. PO yang nilainya melampaui batas matriks otorisasi akan berstatus To Approve.
  2. Approver membuka Approvals, meninjau permintaan, lalu [Approve] atau [Reject].
  3. Setelah disetujui, PO berpindah ke status Purchase Order dan barang boleh diterima gudang.

4.3 Retur Pembelian (PO Return / RTV)

Purchase ▸ Orders ▸ PO Returns → klik [New]

Anda tidak perlu tahu PO mana yang akan dipotong

Cukup masukkan produk dan kuantitas. Sistem akan menelusuri sendiri seluruh PO dan penerimaan dari vendor tersebut, mengambil dari PO tertua lebih dulu (FIFO), dan memakai harga satuan PO asalnya untuk setiap potongan.

  1. Isi Vendor dan Date.
  2. Tambahkan baris: pilih Product dan isi Quantity yang akan diretur. Selesai — jangan isi harga.
  3. Klik [Allocate]. Sistem mengalokasikan kuantitas ke PO/GR/Bill asal secara FIFO. Hasilnya muncul di tab Allocations: terlihat PO mana, harga berapa, dan faktur mana yang mendasarinya.
  4. Periksa hasil alokasi. Jika kuantitas melebihi yang boleh diretur, sistem menolak — lihat kotak peringatan di bawah.
  5. Klik [Validate]. Sistem menghasilkan dua dokumen:
    • Return Picking — barang keluar dari gudang.
    • Vendor Credit Note berstatus draft, dikelompokkan per faktur asal.
  6. Serahkan Credit Note ke AP Officer untuk di-post dan direkonsiliasi (lihat §6.1).
Jika muncul error "over-return"

Artinya kuantitas yang Anda retur melebihi yang tersedia. Batasnya adalah:

Qty diterima − Qty yang sudah pernah diretur − Qty alokasi yang masih pending

Periksa apakah ada PO Return lain untuk vendor & produk yang sama yang masih berstatus Allocated tetapi belum di-Validate.

5. Warehouse — Gudang & DC

Inventory / User · Inventory / Manager Penerimaan barang, scrap, dan stok

5.1 Menerima Barang (Receipt)

Inventory ▸ Overview → kartu Receipts · atau Inventory ▸ Operations ▸ Transfers ▸ Receipts

  1. Buka Receipt yang berasal dari PO yang sudah dikonfirmasi.
  2. Isi kuantitas yang benar-benar diterima pada kolom Quantity.
  3. Untuk produk ber-Lot/Serial, isi atau pindai nomor Lot pada setiap baris.
  4. Klik [Validate].
Sistem MENOLAK penerimaan melebihi PO

Jika kuantitas yang Anda isi lebih besar daripada yang dipesan di PO, [Validate] akan gagal dengan pesan error. Ini disengaja — untuk mencegah barang masuk tanpa dasar PO.

Yang harus dilakukan: terima sebanyak yang tertera di PO. Jika vendor benar-benar mengirim lebih, hubungi Purchasing untuk menerbitkan PO tambahan — jangan memaksakan angka di Receipt.

Sistem juga menolak baris yang tidak berasal dari PO. Anda tidak bisa menambahkan produk baru ke Receipt yang terkait PO.

Apa yang terjadi setelah [Validate]

Stok bertambah, dan sistem otomatis membentuk jurnal: Dr Persediaan / Cr GR/IR Clearing. Akun GR/IR menampung nilai barang yang sudah diterima tetapi fakturnya belum masuk. Anda tidak perlu melakukan apa pun untuk jurnal ini.

5.2 Scrap Batch — Penghapusan Stok Massal

Inventory ▸ Operations ▸ Scrap Batches → klik [New]

Mengapa memakai Scrap Batch, bukan Scrap biasa

Menu Scrap standar Odoo hanya bisa satu produk per dokumen. Scrap Batch memungkinkan banyak produk dalam satu dokumen, dan hanya membentuk satu jurnal — jauh lebih mudah ditelusuri.

  1. Isi Date, Warehouse, Source Location (lokasi asal barang), dan Scrap Location (lokasi pembuangan).
  2. Tambahkan baris untuk setiap produk: Product, Scrap Qty, dan Lot bila ada.
  3. Isi Origin — alasan penghapusan (mis. "Barang rusak gudang DC, BA no. 123").
  4. Warehouse Manager klik [Validate].
Sudah siap dipakai

Akun kerugian scrap sudah dikonfigurasi: 7218000001 — Inventory write-off. Saat Anda klik [Validate], jurnal terbentuk otomatis: Dr 7218000001 Inventory write-off / Cr akun persediaan kategori barang tersebut.

6. AP Officer & Accountant

Invoicing / Billing · Invoicing / Administrator Faktur vendor, pembayaran, dan penutupan

6.1 Membuat Vendor Bill

Invoicing ▸ Vendors ▸ Bills → klik [New]

  1. Isi Vendor dan Bill Date.
  2. Isi Bill Reference — nomor faktur asli dari vendor. Wajib unik. Sistem akan menolak jika nomor ini sudah pernah dipakai untuk vendor yang sama.
  3. Cara tercepat: klik [Add PO] / pilih Purchase Order — baris akan terisi otomatis dari PO, lengkap dengan Purchase Type dan Operating Unit-nya.
  4. Periksa baris. Untuk pembelian Trade, baris produk otomatis diarahkan ke akun GR/IR Clearing — bukan ke COGS. Ini benar; jangan diubah.
  5. Klik [Confirm] untuk mem-post. Nomor dokumen terbentuk otomatis: BILL/T/EBR/… atau BILL/NT/EBR/….
Jika muncul error "duplicate reference"

Berarti Bill Reference yang Anda isi sudah pernah dipakai untuk vendor tersebut. Di Odoo standar ini hanya peringatan; di sistem EBR ini adalah error yang memblokir — sengaja, untuk mencegah faktur ganda. Periksa apakah faktur tersebut sudah pernah diinput.

Untuk Non-Trade: PPh dipotong otomatis

Jika vendor/produknya merupakan objek PPh, sistem otomatis membentuk Withholding Line dan draft Bukti Potong saat Bill di-post. Tarifnya ditentukan sendiri oleh sistem (mis. PPh 23 naik dari 2% ke 4% bila vendor tidak ber-NPWP). Serahkan tindak lanjutnya ke Tax Officer — lihat Bab 9.

6.2 Register Payment + Admin Fee & Card BIN

  1. Buka Bill yang sudah di-post, klik [Register Payment].
  2. Isi Journal (bank/kas), Payment Date, dan Amount.
  3. Pilih Payment Method — tersedia GIRO dan Bank Transfer selain metode standar.
  4. Bila bank memotong biaya administrasi: tambahkan baris pada Admin Fees. Setiap baris punya Account dan Amount sendiri — jadi beberapa jenis biaya dapat masuk ke akun COA yang berbeda dalam satu pembayaran.
  5. Bila pembayaran memakai kartu: isi Card BIN. Sistem mencari tabel BIN/MDR, menghitung MDR-nya, dan membukukannya sebagai potongan.
  6. Klik [Create Payment].
  7. Cetak bukti: buka Payment → [Print] → Payment Voucher (pembayaran keluar) atau Payment Receipt (penerimaan). PDF berisi tabel COA, nominal terbilang dalam Bahasa Indonesia, dan kolom tanda tangan.
Card BIN belum bisa dipakai sampai tabelnya diisi

Tabel Card BIN / MDR saat ini masih kosong. Selama kosong, perhitungan MDR tidak akan berjalan. Lihat §6.5 untuk cara mengisinya.

6.3 Inventory Reconciliation

Invoicing ▸ Accounting ▸ Inventory Reconciliation Finance Manager

Menyelaraskan saldo GL akun persediaan dengan nilai stok riil.

  1. Klik [New]. Isi Date, Journal, dan Counterpart Account (akun selisih/variasi).
  2. Klik [Compute]. Sistem mengisi tabel: per akun valuasi ditampilkan GL Balance, Stock Value, dan Difference.
  3. Periksa baris yang Difference-nya tidak nol. Pahami penyebabnya sebelum melanjutkan — jangan langsung generate.
  4. Bila sudah yakin, klik [Generate Entry]. Jurnal penyesuaian terbentuk. Status berubah menjadi Generated.

6.4 Periodic COGS

Invoicing ▸ Accounting ▸ Periodic COGS Finance Manager

Mengapa COGS dihitung berkala, bukan otomatis per transaksi

Data penjualan toko diimpor lebih dulu daripada data pembeliannya. Akibatnya banyak barang terjual saat harga pokoknya belum ada di Odoo — barang itu dinilai berbiaya nol. Odoo 19 tidak lagi memperbaiki nilai ini secara retroaktif. Karena itu COGS dihitung berkala lewat dokumen ini.

  1. Klik [New]. Isi Date From, Date To, dan Journal.
  2. Klik [Compute]. Sistem menghitung COGS per kombinasi (Operating Unit × Kategori Produk).
  3. Periksa field Zero Cost Qty. Angka ini menunjukkan kuantitas yang masih berbiaya nol. Jika angkanya besar, artinya data pembelian belum lengkap — selidiki dulu.
  4. Bila sudah wajar, klik [Post]. Jurnal terbentuk: Dr COGS / Cr Persediaan.

6.5 Konfigurasi Trade / Non-Trade & Card BIN

Finance Manager Dua tabel konfigurasi yang menentukan ke akun mana angka jatuh.

Trade / Non-Trade Accounts

Invoicing ▸ Configuration ▸ Trade / Non-Trade Accounts

Satu baris per Purchase Type. Isi: Payable Account, GR/IR Account, Expense Account.

Akun GR/IR harus bertipe Current Liability

Jangan memilih akun bertipe Payable untuk GR/IR. Tipe Payable memicu aturan due date Odoo dan akan merusak posting Vendor Bill. Gunakan tipe Current Liability (Liabilitas Lancar).

GR/IR Trade sudah terpasang — jangan diisi ulang

Baris Trade pada tabel ini sengaja dibiarkan kosong pada kolom GR/IR Account. GR/IR untuk barang dagangan ditentukan per kategori produk — 2103109121 textile, …122 footwear, …123 accessories, …124 miscellaneous — dan semuanya sudah benar.

Jika Anda mengisi kolom GR/IR pada baris Trade, isian itu akan MENIMPA pemetaan per-kategori dan seluruh barang dagangan akan masuk ke satu akun GR/IR yang sama. Biarkan kosong.

Card BIN / MDR

Invoicing ▸ Configuration ▸ Card BIN / MDR → klik [New]

  1. Isi Card Scheme (Visa, Mastercard, dsb.).
  2. Isi rentang BIN From – BIN To (digit awal nomor kartu).
  3. Pilih Acquirer Bank.
  4. Isi MDR Percent dan/atau MDR Fixed, serta MDR Account (akun beban MDR).
  5. Isi masa berlaku Date Start – Date End.
Rentang BIN tidak divalidasi sistem

Sistem tidak memeriksa apakah rentang BIN saling tumpang tindih. Periksalah secara manual — rentang yang tumpang tindih akan membuat perhitungan MDR tidak dapat diprediksi.

7. Asset Officer — Aktiva Tetap

Asset User · Asset Manager Registrasi, depresiasi, revaluasi, pelepasan

7.1 Registrasi Aset Baru

Invoicing ▸ Assets ▸ Fixed Assets → klik [New]

  1. Isi Name aset dan Asset Group. Enam grup EBR yang tersedia: Land · Building & Improvements · Vehicles · Office & Outlet Equipment · Machinery · Furniture & Fixtures. Grup inilah yang menentukan akun aset, akumulasi depresiasi, dan beban depresiasi.
  2. Isi Acquisition Value (nilai perolehan), Salvage Value (nilai sisa), Useful Life (umur manfaat, dalam bulan), dan tanggal perolehan.
  3. Pilih Location — lokasi fisik aset.
  4. Klik [Confirm]. Status berubah menjadi Running dan jadwal depresiasi garis lurus terbentuk otomatis.
Keenam grup sudah siap

Seluruh grup ber-depresiasi kini punya akun akumulasi depresiasi dan jurnal depresiasi (DEPRE). Contoh untuk Vehicles: aset 1205103000, akumulasi 1205202000, beban 7204102000.

Land sengaja tidak punya akun depresiasi — tanah tidak disusutkan.

7.2 Posting Depresiasi

Invoicing ▸ Assets ▸ Post Depreciation

Saat ini depresiasi TIDAK berjalan otomatis

Scheduled Action "Custom Asset: Post Monthly Depreciation" sengaja masih nonaktif. Artinya Anda harus memposting depresiasi secara manual dari menu ini setiap bulan.

Alasannya: sekali cron itu diaktifkan, ia langsung memposting seluruh baris depresiasi yang sudah jatuh tempo — bisa banyak sekaligus dan sulit ditarik kembali. Aktifkan hanya setelah Finance melihat dampaknya lewat posting manual.

Jurnal yang terbentuk: Dr Beban Depresiasi / Cr Akumulasi Depresiasi.

7.3 Revaluasi & Pelepasan

Revaluasi (PSAK 16 / IAS 16)

Invoicing ▸ Assets ▸ Revaluations

  1. Buat Revaluation baru, pilih aset, isi nilai wajar yang baru.
  2. Sistem membandingkan dengan nilai buku dan membukukan hasilnya:
    • Nilai wajar > nilai buku → Surplus masuk ke OCI (akun 3005200004).
    • Nilai wajar < nilai buku → Rugi masuk ke P&L (akun 7706000000).

Pelepasan (Disposal)

  1. Buka aset yang akan dilepas, jalankan Disposal Wizard.
  2. Isi harga jual. Sistem menghitung gain/loss terhadap nilai buku bersih (NBV).
  3. Status aset berubah menjadi Disposed.

7.4 Asset Register

Invoicing ▸ Assets ▸ Asset Register

  1. Buka menu. Wizard parameter muncul.
  2. Isi Year (tahun laporan) dan pilih Assets — mis. Running only untuk aset yang masih berjalan saja.
  3. Opsional: batasi dengan Groups (kategori aset) dan/atau Locations.
  4. Klik [Print PDF] atau [Export Excel].

Saat AP Officer mem-post Vendor Bill, sistem sudah memeriksa vendor dan produknya terhadap 107 kode objek pajak EBR, lalu membentuk potongan PPh berikut draft Bukti Potong. Anda tidak perlu menghitung manual — Anda perlu memeriksa dan melengkapi.

  2. Periksa: apakah kode objek pajaknya benar? Apakah tarifnya sesuai?

11.2 Troubleshooting — Pesan Error yang Sering Muncul

GejalaPenyebabSolusi
[Validate] Receipt gagal — pesan tentang kuantitas berlebih Kuantitas diterima melebihi kuantitas PO. Diblokir sistem secara sengaja. Terima sesuai PO. Bila vendor memang mengirim lebih, minta Purchasing menerbitkan PO tambahan.
[Validate] Scrap Batch gagal — pesan tentang account Parameter scrap_loss_account_code kosong. Sudah diperbaiki (7218000001) — seharusnya tidak muncul lagi. Jika tetap muncul, periksa parameter itu di Settings ▸ Technical ▸ System Parameters (§10.1).
Posting Vendor Bill gagal — pesan tentang due date Akun GR/IR salah tipe — dipilih Payable, seharusnya Current Liability. Ubah tipe akun GR/IR menjadi Current Liability (§6.5).
Vendor Bill ditolak — duplicate reference Nomor faktur vendor sudah pernah dipakai. Periksa apakah faktur sudah pernah diinput. Ini blokir yang disengaja untuk mencegah faktur ganda.
Confirm aset gagal — "depreciation journal must be set" atau akun akumulasi kosong Grup aset belum punya jurnal depresiasi / akun akumulasi. Sudah diperbaiki untuk keenam grup (jurnal DEPRE). Jika muncul pada grup baru yang Anda buat sendiri, isi Journal dan akun-akunnya di Invoicing ▸ Assets ▸ Configuration ▸ Groups (§7.1).
PO Return ditolak — over-return Kuantitas retur melebihi batas (diterima − sudah diretur − alokasi pending). Periksa PO Return lain yang masih berstatus Allocated tapi belum Validate (§4.3).
Impor berstatus Partial — banyak baris error SKU tidak ada di master X101, atau format kolom berkas berubah. Impor ulang X101 terbaru; atau perbaiki Data Start Row / Column Map pada Import Profile (§2.3–2.4).
Pendapatan masuk ke akun "Others" Produk hasil impor tidak punya kategori, sehingga tidak terpetakan ke akun pendapatan yang benar. Pastikan X101 terbaru sudah diimpor dan x24_strict_product = 1 agar SKU tak dikenal diparkir, bukan dibuat asal.
Berkas sudah ditaruh di folder tapi tidak terproses Scheduled Action "Retail Import: poll feeds" masih nonaktif. Aktifkan di Settings ▸ Technical ▸ Scheduled Actions (§10.2).
Saldo POS Suspense Clearing tidak nol X24DN sudah diimpor, X70D belum. Impor X70D untuk hari dagang yang bersangkutan (§2.1).
