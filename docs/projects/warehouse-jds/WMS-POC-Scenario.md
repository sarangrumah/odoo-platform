# WMS POC Scenario — by transaction category

End-to-end proof of concept for the Odoo 19 WMS stack, walked **per transaction
category** rather than per module, so a client can sign off category by
category. Built and verified on **`demo_wms`**, with the same module set and
versions as the reference implementation **`rnd_wms`**.

Everything below is executed by one script against real records — no mocks:

```bash
docker exec -i odoo19-platform-odoo-mgmt odoo shell -d demo_wms --no-http \
    < scripts/tenants/wms_demo/80_poc_scenario.py
```

It prints PASS / PARTIAL / FAIL per step with the evidence used, and writes the
printable output to `/var/lib/odoo/poc_wms/POC<nn>/` inside the Odoo container.
Re-running is safe: the warehouse and its configuration are created once and
reused, and each run creates a fresh transaction batch tagged `POC<nn>`.

Latest run: **14 / 14 PASS**.

---

## 1. What the POC builds

A second warehouse, **POC Distribution Centre (`POC`)**, deliberately configured
with **2-step reception** and **2-step delivery** so that putaway and picking
are each a leg of their own:

```
Receipts (POC/IN)  →  Storage (POC/STOR)  →  POC/Stock/<zone>/<bin>
                         ↑ putaway leg — this is what the slotting engine slots

POC/Stock  →  Pick (POC/PICK)  →  POC/Output  →  Delivery (POC/OUT)  →  Customer
                 ↑ "Picking (Out)"                   ↑ "Delivery Order"
```

| Zone | Bins | Storage category | Purpose |
|---|---|---|---|
| Bulk Pallet | `POC-BLK-01…06` | POC Bulk — Pallet Only (`same` product, 1600 kg, 2 pallets) | pallet reserve |
| Forward Pick | `POC-PCK-01…06` | POC Pick — Mixed Carton (`mixed`, 300 kg, 12 cartons) | piece pick |
| Pack & Ship | `POC-PAK-01` | POC Pack — Staging (`mixed`, 500 kg, 40 cartons) | staging |

Every bin is barcoded, carries a volume capacity and a walk sequence. Four
products cover the tracking modes the warehouse has to handle: lot-tracked with
expiry, lot-tracked, untracked, and **serial/IMEI**.

## 3. Reporting — barcodes at transaction *and* line-item level

This was the explicit requirement: every report must carry a barcode for the
**transaction** and for each **line item**, in PDF or Excel.

### 3.1 PDF documents

| Report | Model | Transaction barcode | Line-item barcode |
|---|---|---|---|
| Picking List | `stock.picking` | picking name (Code128) | item barcode + location QR per line |
| Packing List | `stock.picking` | picking name (Code128) | package Code128 + QR per block |
| Barcode List (scan sheet) | `stock.picking` | — | every package + product barcode, QR and Code128 |
| Product Label / Price Tag | `product.product` | — | one barcode per sticker |
| Stock Take / Spot Check | `custom.cycle.count.session` | session name (Code128) | lot or SKU per count line |
| **Scrap Note** *(new)* | `stock.scrap` | note reference (Code128) | lot or SKU per scrapped line |

The Picking List now also prints for **receipts**, so a goods-receipt sheet is
the same document the picker and the putaway operator already know.

### 3.2 XLSX exports

Every WMS analysis report exports to a workbook with **two barcode image
columns** — `Document Barcode` (column A) and `Item Barcode` (column B) —
followed by the data columns, one flat header row, autofilter and a totals row:

| Report | Document barcode | Item barcode |
|---|---|---|
| Transfer Report | picking | lot / SKU |
| Stock Summary (qty + value) | bin | lot / SKU |
| Stock Take | count session | lot / SKU |
| Purchase Return | picking | SKU |
| **Scrap Report** *(new)* | scrap order | lot / SKU |

Use the **Export XLSX (with barcode)** button in the list header. With rows
selected it exports the selection; with nothing selected it exports the whole
report.

### 3.3 Symbology

- **Document** barcodes are Code128 — references contain `/`.
- **Item** barcodes are rendered `auto`: a 13-digit payload comes out as a real
  **EAN-13**, everything else falls back to Code128. This matters because
  handhelds are routinely shipped with Code128 decoding switched off (the Denso
  BHT units on this project read EAN-13 only).

## 4. Platform gotchas found and fixed while building this

These are real defects the POC surfaced; all are fixed in the code, but they
are the kind of thing that bites again elsewhere.

1. **Report CSS and charset were being silently dropped.**
   `ir_actions_report._prepare_html` keeps only the *children of `<main>`* and
   writes them to a bare `.html` file — no `<head>`. Every "self-contained"
   report wrapper on this platform therefore printed **unstyled**, and non-ASCII
   text (`—`, `✓`, Indonesian characters) came out as mojibake. Fixed by moving
   the `<style>` and `<meta charset="utf-8">` **inside `<main>`** in all six WMS
   templates.

2. **Every cycle-count session was named `CC/NEW`.**
   `data/ir_sequence_data.xml` in `custom_wms_cycle_count` was a placeholder
   stub, so `next_by_code` returned `None` and `create()` fell back to a
   literal — making the session barcode unscannable and report grouping
   impossible. Fixed with a real sequence (`CC/%(year)s/00001`) plus a migration
   that renumbers existing placeholder sessions. (Same class of bug as the
   `TO/NEW` one previously fixed in the TO engine.)

3. **SQL-view reports could read stale data.**
   An `_auto=False` model only flushes *itself*, so a scrap validated earlier in
   the same transaction still read as `draft` through the view. All five report
   models now declare `_depends` on their underlying models.

4. **Barcodes are embedded, not fetched.**
   Report barcodes are now rendered in-process to `data:image/png;base64,…`
   rather than `<img src="/report/barcode/…">`, so wkhtmltopdf makes no HTTP
   callback per barcode.

5. **`odoo shell --no-http` makes every PDF look broken.**
   With no HTTP server, wkhtmltopdf times out on its callback and takes ~60 s
   per document (core Odoo's own delivery slip takes ~123 s under the same
   conditions). The PDFs are still produced correctly. Over real HTTP the same
   documents render in **2.6–6.2 s**. Do not diagnose report performance from a
   shell run.

6. **New Python needs a web-container restart.**
   Upgrading a module from the management container updates the database, but
   the long-running web workers keep the old code in memory — a newly added
   method 500s until `docker restart odoo19-platform-odoo`.

```bash
for f in 10_seed_warehouse 20_seed_products 30_seed_inbound 40_seed_outbound \
         50_config_wms 51_config_native_slotting 60_admin_login 99_verify; do
  docker exec -i $ODOO odoo shell -d demo_wms --no-http \
      < scripts/tenants/wms_demo/$f.py
done

# The POC walkthrough (repeatable, one transaction batch per run)
docker exec -i $ODOO odoo shell -d demo_wms --no-http \
    < scripts/tenants/wms_demo/80_poc_scenario.py

# Collect the printable evidence
docker cp odoo19-platform-odoo-mgmt:/var/lib/odoo/poc_wms/POC05 ./poc-evidence
```

For a live demo, drive the same flow through the UI and print from the
**Print** menu on each document; the script exists to prove the chain works and
to produce the evidence pack.
